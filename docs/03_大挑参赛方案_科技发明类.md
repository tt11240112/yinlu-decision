## 零、先说结论

**你们不该去写问卷调查报告。** 理由很实在：

| 问题 | 现实 |
|---|---|
| 没学过社会调查方法 | 问卷设计、抽样、信效度检验都是专业活，现学来不及 |
| 不会数据分析 | SPSS 建模、回归分析不是一周能学会的 |
| 访谈不现实 | 找不到足够多的高三学生和家长，样本量不够就是硬伤 |
| **而且你们有更好的牌** | 你们是计算机 + 网安专业，**能做出真东西**，这是别人没有的 |

**大挑不只有问卷一条路。** 它有三个类别：

| 类别 | 核心材料 | 适合谁 |
|---|---|---|
| 自然科学类学术论文 | 有实验/理论创新的论文 | 做科研的 |
| **哲学社会科学类调查报告** | 问卷 + 访谈 + 统计分析 | 社科专业（**不是你们**） |
| **科技发明制作类（A/B）** | **技术报告 + 可运行系统** | **你们** ✅ |

**推荐报：科技发明制作类 B 类**（投入较少、为生产技术或社会生活带来便利的小发明/软件作品）。

## 一、科技发明类要交什么

| 材料 | 说明 | 谁负责 |
|---|---|---|
| **作品申报书** | 学校发的模板，填基本信息 + 作品简介 | G0 |
| **作品说明书（技术报告）** | **核心**，8000-15000 字 | 全员分工，G0 统稿 |
| **可运行的系统** | 就是你们的网站 | 全员 |
| **答辩 PPT + 现场演示** | 10-15 分钟 | G0 + G3-A |

**注意**：科技发明类**不要求问卷**，但要求：
- 科学性（技术方案合理）
- 先进性（比现有方案好在哪）
- 实用性（真能解决问题）
- **创新性**（这是评分重点）

## 二、技术报告大纲（照着写）

> ⚠️ **字数按 8000-10000 字写**，不是 13000 字。
> 各校要求：洛阳师范学院 8000 字以内、山东石油化工学院 10000 字以内。
> 下面各章字数是按 13000 字给的，**按 6 折压缩即可**，重点保第 4、6 章。
>
> ⚠️ **报名前必须先解决三件硬门槛**：软著/专利、2 名高级职称指导老师、团队人数上限。
> 详见 `04_参赛硬性条件与软著申请.md`——**其中软著本周就要启动，是全项目唯一有外部周期的事项。**
>
> 每人负责自己那部分，G0 最后统稿。

### 第 1 章 立题背景与意义（1500 字）— G0

- 高考志愿填报 / 升学决策的信息困境
- 现有信息渠道的问题：机构收费高、信息不透明、无法验证回答者身份
- 本作品的目标：构建**可验证、可追溯、抗操纵**的教育决策信息平台
- 现实意义：呼应"清朗"网络空间治理

### 第 2 章 相关研究现状与问题分析（2000 字）— G0 + G2

- 国内外同类产品调研（表格对比）：

| 产品 | 类型 | 信息可信机制 | 不足 |
|---|---|---|---|
| 掌上高考 | 官方数据平台 | 官方背书 | 无个体经验，不能问"这个专业累不累" |
| 知乎/贴吧 | UGC 社区 | 无 | 身份不可信，水军与软文泛滥 |
| 各类志愿卡 | 商业服务 | 付费 | 价格高，算法不透明 |
| **本作品** | 可信 UGC | **可验证匿名凭证 + 内容存证 + 风控** | — |

- 提炼出三个核心问题：
  1. **身份不可信**：无法判断回答者是否真是该校学生
  2. **内容可篡改**：回答被修改后无痕迹
  3. **评价可操纵**：刷好评、水军无成本

### 第 3 章 系统总体设计（2000 字）— G1 + G4-B

- 整体架构图（前端 / 后端 / 安全层 / 数据层）
- 技术选型及理由
- 模块划分（对应你们的 26 个 JS 模块）
- 数据库设计（ER 图 + 主要表结构）

### 第 4 章 关键技术实现（3000 字）— 各组写自己的

**4.1 可验证匿名凭证（G3-A）**
- 基于 Ed25519 的签发与验证流程
- 选择性披露：展示"某 985 · 计算机 · 2023 级"，但不暴露真实身份
- 关键代码与流程图

**4.2 内容完整性存证（G3-A）**
- 每条回答生成 SHA-256 哈希
- Merkle 树批量锚定，降低存储成本
- 篡改检测：改一个字就显示"完整性校验失败"

**4.3 反共谋风控（G3-B）**
- 信誉图算法（回答者可信度传播）
- 共谋检测：同设备指纹 / 同 IP 段聚集识别
- 异常打分与处置策略

**4.4 高考位次查询与志愿匹配（G2-A + G4-A）**
- 数据模型：院校 × 年份 × 省份 × 位次
- 匹配算法：基于历史位次的概率估计
- 数据来源与清洗流程

**4.5 移动优先前端架构（G1）**
- 免构建的多文件拆分方案（你们正在用的）
- 响应式设计与性能优化

### 第 5 章 创新性（1000 字）— G3 主笔

写 3-5 条，每条要有"现有方案怎么做 → 我们怎么做 → 好在哪"：

1. **可验证匿名凭证**：把"可信"和"隐私"从二选一变成兼得
2. **内容哈希存证**：让 UGC 内容不可静默篡改
3. **信誉图 + 共谋检测**：把反水军从人工审核变成算法自动识别
4. **隐私优先架构**：数据最小化 + 本地优先存储
5. **面向教育垂直场景的信任设计**：通用信任机制在教育场景的落地

### 第 6 章 系统测试与验证（2000 字）— G3-B 主笔 ⭐

**这一章是你们网安专业的主场，也是最容易出彩的部分。**

#### 6.1 功能测试
- 各模块测试用例表（输入 → 预期 → 实际 → 结论）

#### 6.2 安全测试（重点）
| 测试项 | 方法 | 结果 |
|---|---|---|
| XSS 注入 | 在回答框输入 `<script>alert(1)</script>` | 被转义，未执行 ✅ |
| CSRF 攻击 | 构造跨站请求 | 被 Token 校验拦截 ✅ |
| 越权访问 | 用 A 账号尝试修改 B 的数据 | 被拒绝 ✅ |
| **本地存储篡改** | F12 修改 localStorage 伪造"已认证学长" | v1 可伪造，v3 已加入签名校验 ✅ |
| 密码存储 | 检查是否明文 | 已加盐哈希 ✅ |
| 输入验证 | 超长输入、特殊字符 | 有边界校验 ✅ |

> 💡 **把"本地存储篡改"这一条做成亮点**：
> 先承认早期版本存在问题（F12 就能伪造身份），然后展示你们如何发现、
> 如何设计签名校验方案、如何验证修复。
> **"发现问题 → 分析问题 → 解决问题"的完整闭环，比假装没问题有说服力得多。**

#### 6.3 性能测试
- 首屏加载时间（优化前后对比）
- 300 所院校数据查询响应时间
- 后端 100 并发压测结果

- 社会价值：降低信息不对称、治理教育信息生态乱象
- 可持续运营模式（不夸大，写清楚就行）

### 5 分钟安全演示脚本（全场最独特的部分）

```
1. 【1 分钟】打开网站，点开一条回答
   "这里显示'已认证 · 某 985 · 计算机 · 2023 级'。
    评委老师可能会问：这个认证是真的吗？"

2. 【1 分钟】按 F12 打开控制台，直接改 localStorage
   "在旧版本里，我改一个字段，刷新——
    看，我变成了'已认证 · 清华 · 计算机'。
    这就是我们发现的第一个问题：信任链本身是假的。"

3. 【2 分钟】切到新版本，重复同样操作
   "现在我们加入了签名校验——
    改了之后，页面立刻显示'凭证校验失败，该认证无效'。
    因为我们用 Ed25519 对凭证签了名，本地改不了。"

4. 【1 分钟】演示内容存证
   "同样，我改一个字，这条回答立刻显示'完整性校验失败'。"

5. 收尾
   "我们团队来自网络空间安全学院，
    所以我们做的不是又一个信息平台，
    而是一个'信息本身可验证'的基础设施。"
```

> **这个演示为什么强**：全场唯一一个需要评委亲眼看到"攻击被拦截"的作品。
> 别的队伍讲功能，你们讲安全——这是降维打击。

## 四、关于"后端还是空的"怎么办

### 现实评估

| 方案 | 时间 | 效果 | 建议 |
|---|---|---|---|
| 不做后端 | 0 | 系统仍是可演示的原型 | ❌ 科技发明类会扣分 |
| **最小后端** | **1-2 周** | 用户注册登录 + 数据持久化 | ✅ **推荐** |
| 完整后端 | 1-2 月 | 全功能 | 大挑后来做（半年路线图） |

### 最小后端做什么（W2-W3，G4-B 负责）

只要四件事：

1. **用户注册/登录**（JWT 鉴权）
2. **内容存取 API**（发布回答、获取回答列表）
3. **院校数据 API**（替代本地写死的数据）
4. **部署上线**（Render / Railway 免费额度够用）

技术栈（最简单路线）：
```
Node.js + Express + SQLite
```

为什么选这个：
- 全是 JavaScript，前端同学也能帮忙
- SQLite 不用装数据库服务，就是一个文件
- 网上教程最多，遇到问题好查

**交付标准**：W3 结束时，前端能调通 `/api/login`、`/api/answers`、`/api/institutions` 三个接口。

### 做不出来的兜底方案

如果 W3 后端确实没跑通：
- 前端继续用 localStorage（不影响演示）
- 在技术报告第 3 章写清楚**后端架构设计**（含 API 设计、数据库 ER 图）
- 第 8 章"展望"里说明后续计划

**诚实说明"已完成设计、正在实现"比吹牛被拆穿好得多。**

## 七、给你们的三个提醒

1. **不要为了"看起来完整"堆功能。**
   科技发明类看的是"解决一个真问题，解决得有多好"。
   把信任体系做透，比做 20 个半成品功能强得多。

2. **技术报告要边做边写，不要最后补。**
   最后一周补 13000 字，质量必然崩。W2 就开始写第 1-2 章。

3. **保留所有过程证据。**
   拆分前的旧版截图、修复前后的对比、测试记录——
   这些都是"你们真的做了这件事"的证据，答辩时很有用。
