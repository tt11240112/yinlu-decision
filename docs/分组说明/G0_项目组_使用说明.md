### 关于 `template/index.html`（新东西，重点看）

根目录的 `index.html` 是**自动生成**的，手改会被覆盖。
**HTML 源文件是 `template/index.html`**，改它然后跑脚本：

```bash
node tools/build-index.js
```

模板里只有两行是"占位符"，跑脚本时会被替换，**别在这两行上写东西**：

```html
<script src="./app.js" defer></script>        ← 会变成 26 个 js 标签
<link rel="stylesheet" href="styles.css">     ← 会变成 15 个 css 标签
```

其余内容（页面结构、导航、文案）会**原样保留**到生成的 `index.html`。

## 2. 你认领的文件详解

### 2.1 `js/03-config-constants.js`（147 行，原 app.js 238–379 行）

**作用**：全站配置中枢。包含 `STORE`（localStorage 所有键名）、静态常量、所有"当前状态"变量。

**里面有 56 个变量**，最重要的：

| 变量 | 用途 |
|---|---|
| `STORE` | localStorage 所有键名集合（**加键必须先加这里**） |
| `CYBER_PET_AVATARS` | 电子宠物形象配置 |
| `THEME_NAMES` | 主题名称列表 |
| `REGION_CITIES` | 城市库（省份 → 城市） |
| `MAJOR_CATEGORIES` / `MAJOR_CATEGORY_BY_NAME` | 专业分类 |
| `currentStage` | 当前阶段（高考/考研/就业） |
| `currentSearch` / `currentSchoolSearch` / `currentMajorSearch` | 各类搜索关键词状态 |
| `currentInstitutionRegion` / `currentExperienceRegion` 等 | 地区/专业筛选状态 |
| `EXPERIENCE_DIMENSIONS_BY_SOURCE` | 经验维度定义 |

**你什么时候改它**：
- 有人要加新的 localStorage 键 → 你加到 `STORE`
- 有人要加新的全局状态变量 → 你加到这里
- 要改主题名、城市库、专业分类

**改了影响谁**：**几乎所有人**。这个文件被 18 个文件引用。

> ⚠️ **所以规矩是：别人要加常量，找你加，或者你审 PR 时重点看这里。**
> 谁都往这个文件里塞东西，很快就乱。

**加 localStorage 键的正确方式**：
```javascript
const STORE = {
  users: "yinlu_users",
  // ... 已有的
  myNewKey: "yinlu_my_new_key",   // ← 加一行，别在别处直接写字符串
};
```

### 2.2 `js/25-bootstrap.js`（27 行，原 app.js 3636–3657 行）

**作用**：页面加载完执行的初始化流程。

**它依次做了这些事**：
1. 应用主题、应用布局（横版/竖版）
2. 渲染决策倒计时和日历
3. 恢复宠物位置和形象、初始化拖动
4. 设置当前阶段、更新账户头部
5. 刷新图标、切问答 Tab、更新回顶按钮
6. 未登录 → 0.5 秒后弹账户窗；已登录 → 0.9 秒后启动新手指引

**你什么时候改它**：
- 有新功能需要在页面打开时初始化
- 要调整启动顺序

**注意事项**：
- **它倒数第二个加载**（26 号是家庭覆盖版），所以能调用前面所有函数
- 加初始化代码要**放在依赖之后**。比如你的代码依赖宠物，就得放在宠物初始化那行之后

## 3. 怎么用这个文件夹（你的日常流程）

### 每天开工（30 秒）

```bash
git checkout v3            # ⚠️ 主线是 v3，不是 main
git pull origin v3
```

> 用 GitHub Desktop 的话：左上角切到 `v3` → 点 **Fetch origin**。

### 改代码时（你自己的三块：03 号 / template / server）

1. 改文件
2. **动了 `template/index.html` 或新增了 js/css 文件** → 跑 `node tools/build-index.js`
3. F12 打开控制台，**确认零红色报错**
4. 提交到自己的分支 → 提 PR

### 🆕 审 PR：现在大部分不用你管了

以前要你手工核对"他改的文件是不是他的"——**现在 CODEOWNERS 替你做了**：
改了谁的文件，GitHub 会自动把那个人加进 Reviewers。

**你需要处理的只有这三类：**

| 情况 | 你要做什么 |
|---|---|
| **跨组改动**（PR 里有两个组的文件） | 你来审，重点看有没有踩别人的坑 |
| **动了 `tools/` `template/` `.github/`** | 必须你审（CODEOWNERS 写的是你） |
| **没人被自动指派** / 卡了超过 1 天 | 你兜底处理 |

**同组搭档互审就够了**（P2↔P3、P4↔P5、P6↔P7、P8↔P9、你↔P9），别抢他们的活。

> ⚠️ **别卡 PR**。小改动 2 小时内必须处理完，否则队员会阻塞。
> 你的角色是兜底，不是挑刺。
