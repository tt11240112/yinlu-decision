### `js/05-core-security.js`（55 行）安全与身份核心 ⭐

**作用**：令牌生成、密码处理、当前用户、角色判断。

| 函数 | 说明 |
|---|---|
| `secureRandomToken(length)` | 生成随机令牌（字母表去掉易混字符 0/1/I/O） |
| `safeExternalHref(url)` | 外链安全校验（防 `javascript:` 伪协议） |
| `createPasswordRecord(pwd)` | 创建密码记录 |
| `passwordMatches(pwd, record)` | 校验密码 |

| 变量 | 说明 |
|---|---|
| `currentUser()` | **返回当前登录用户**（被 10 个文件调用，最重要的一个） |
| `isStudentRole` / `isParentRole` | 角色判断 |
| `userFavorites` | 用户收藏 |
| `candidateStatuses` | 候选状态 |
| `uid` / `majorCandidateId` / `majorDecisionKey` | ID 生成相关 |

> ### ⚠️ 现状：这是已知缺陷，也是你们的改进方向
>
> 现在 `currentUser()` 只是从 localStorage 读，**没有任何校验**。
> 用户按 F12 改一行就能把自己变成"已认证学长"。
>
> **改进方向**（按难度递增）：
> 1. **HMAC 签名**：localStorage 里的用户数据附带签名，改动后验签失败
> 2. **后端校验**（依赖 G4-B 的后端，长期方案）
> 3. **可验证匿名凭证**（Ed25519，见第 4 节）

## 4. 你这一组还缺什么（本组专属缺口）

这是**全项目最重要的缺口清单**。按优先级排：

### 🔴 P0：必须做出来（这是项目的立身之本）

#### 1. 可验证匿名凭证（A 角主责）

**要解决的问题**：如何展示"已认证 · 某985 · 计算机 · 2023级"，同时又**无法反推真人**？

**技术方案**：
- 用 **Ed25519** 签名（椭圆曲线）
- 学校/第三方作为**签发方**，用私钥对"该用户是某校某专业学生"这一事实签名
- 网站只存签名后的凭证，**无法反推用户身份**
- 任何人可用公钥验证签名真伪

> ### ⚠️ 技术实现的重要建议
>
> **不要自己实现椭圆曲线签名。** 你们大二，大概率还没学密码学，
> 写错一行就是安全漏洞，网安方向的评委一眼看穿。
>
> **用成熟库**：`tweetnacl.js`（11KB，纯 JS，Ed25519 签名/验签开箱即用）
>
> 答辩时说 **"我们基于成熟的 Ed25519 实现（tweetnacl）构建了凭证体系"**
> —— 比说"我们实现了 Ed25519"**专业得多**。评委欣赏知道自己边界的人。

**降级方案**（如果做不出来）：
- 用 HMAC-SHA256（Web Crypto API 原生支持，不需要额外库）做本地签名校验
- 虽然不是"匿名凭证"，但至少能证明"数据没被篡改"
- **诚实说明局限**，比硬撑好

#### 2. 内容哈希与防篡改（A 角主责）

**要解决的问题**：改一条回答，应该能被发现。

**方案**：
- 每条内容存一个哈希值
- 多条内容组织成 **Merkle 树**，根哈希定期锚定（可写入日志或后端）
- 内容被改 → 哈希不匹配 → 页面显示"⚠️ 完整性校验失败"

**这个做起来比凭证简单**，建议**先做这个**建立信心。

#### 3. 安全测试报告（B 角主责）⭐ 最确定的得分项

**这是你们专业课学过、最容易出成果的一项。**

对着网站做一遍测试，写进报告。已知必测项：

| 测试项 | 现状（已知问题） | 修复方案 |
|---|---|---|
| **本地存储篡改** | ❌ F12 改 localStorage 可伪造认证 | HMAC 签名校验 / 后端校验 |
| **XSS** | ⚠️ 大部分已用 `escapeHtml`（138 处），但**未全覆盖** | 全量排查用户输入渲染点 |
| **CSRF** | N/A（暂无后端） | 后端上线后加 token |
| **越权访问** | ❌ 无权限模型 | 加角色校验（已有 `isStudentRole`/`isParentRole`） |
| **外链安全** | ✅ 已有 `safeExternalHref` | 检查是否所有外链都过了 |
| **密码存储** | 需检查 `createPasswordRecord` 的实现强度 | 确认是否加盐、迭代次数 |

**写法建议**（这比假装没问题有说服力得多）：
> "我们发现系统在 X 处存在 Y 风险，攻击者可通过 Z 方式利用。
> 我们采用 X 方案修复，并通过 A 测试验证攻击已被拦截。"

**"发现问题 → 修复 → 验证拦截"的完整闭环，比宣称"我们的系统很安全"强十倍。**

#### 5. 《隐私合规白皮书》（B 角主责）⭐ 网安学生最专业

**这是你们最容易做出"别人做不出来"的材料。**

内容建议：
- 数据最小化原则：我们收集哪些数据、为什么必须收集
- 匿名化方案：凭证如何在不暴露身份的前提下证明资质
- 用户权利：查看/导出/删除自己的数据
- 合规性：对照《个人信息保护法》《数据安全法》逐条说明
- 威胁模型：我们假设攻击者能做什么，我们如何防御

> **这一份材料在答辩时是杀手锏。** 别的参赛队交的是"我们做了个网站"，
> 你们交的是"我们做了个网站 + 我们想清楚了它的安全与隐私边界"。
