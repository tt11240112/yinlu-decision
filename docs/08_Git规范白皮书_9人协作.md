## 核心理念

**9 个人改同一个代码库，规范是生命。**

- 没有规范 = 每天花 2 小时解决 merge 冲突，写不了代码
- 有规范 = 各自独立工作，冲突从 90% 降到 10%，效率翻倍

**本文档的三个作用**：
1. **防灾**：预防冲突（比解决冲突省时间 100 倍）
2. **应急**：冲突了也能快速解决
3. **追责**：任何问题都能看到是谁什么时候改的

## 一、分支策略（最重要的规则）

### 1.1 两层分支体系（简化版）

```
main (主分支，保护状态)
  ↑ PR 合并，G0 审核
  |
feat/xxx (G0 个人分支)
feat/xxx (G1 个人分支)
feat/xxx (G2 个人分支)
...
feat/xxx (G8 个人分支)
```

**核心原则**：
- **main** 是受保护的主分支，只能通过 PR 合并
- 每个人从 main 创建自己的个人分支 `gX-功能描述`
- 改完提 PR 到 main，G0 审核后合并
- 合并后删掉旧分支，下次新功能再开新分支

### 1.2 每种分支的用途

| 分支名 | 谁创建 | 从哪来 | 合并到哪 | 生命周期 |
|--------|--------|--------|---------|---------|
| `main` | G0 | 初始化 | — | 永久 |
| `g0-功能名` | G0 | `main` | `main` | 1-5 天 |
| `g1-功能名` | G1 | `main` | `main` | 1-5 天 |
| `g2-功能名` | G2 | `main` | `main` | 1-5 天 |
| ... | ... | `main` | `main` | 1-5 天 |

### 1.3 规则（必须遵守）

✅ **必须做**：
- 新功能必须从 `main` 开一个新分支 `gX-功能名`
- 分支名必须带组号（`g0-`、`g1-`、`g2-` 等），否则看不出谁改的
- 只改你认领的文件（见 02_9人分工与文件认领表.md）
- 一个分支只干一件事（做完立刻提 PR 合并，别攒着）
- 提 PR 前先 pull main 最新代码，避免冲突
- PR 由 G0 审核合并

❌ **绝对禁止**：
- 直接在 `main` 上改代码
- 分支名用中文或特殊符号
- 改别人认领的文件（除非协商好）
- 攒了 5 个功能在一个分支里才提 PR
- 分支放着不管超过 5 天

## 二、提交规范（Commit Message）

### 2.1 格式

```
<type>(<scope>): <subject>

<body>（可选）

<footer>（可选）
```

### 2.2 具体例子

✅ 好的提交：
```bash
git commit -m "feat(gaokao): 新增院校列表页面的地区筛选功能"
git commit -m "fix(auth): 修复登录后刷新页面用户状态丢失的 bug"
git commit -m "refactor(core): 拆分 storage.js 模块，降低耦合"
git commit -m "docs(readme): 补充移动端适配说明"
git commit -m "style(header): 统一导航栏宽度为 16px padding"
```

❌ 不好的提交：
```bash
git commit -m "update"                    # 太模糊
git commit -m "修改了gaokao.js"           # 没说改了什么
git commit -m "bug fix"                   # 没说是什么 bug
git commit -m "W1 任务"                   # 没说功能是什么
```

### 2.3 Type 类型

| 类型 | 说明 | 例子 |
|------|------|------|
| `feat` | 新功能 | `feat(gaokao): 新增院校筛选` |
| `fix` | 修复 bug | `fix(login): 修复登录后跳转错误` |
| `refactor` | 重构代码（功能不变） | `refactor(core): 拆出 storage 模块` |
| `style` | 代码风格、格式（不影响逻辑） | `style(header): 调整 padding` |
| `docs` | 文档 | `docs(readme): 添加安装步骤` |
| `test` | 测试 | `test(auth): 新增登录测试用例` |
| `chore` | 构建、依赖、工具 | `chore: 升级 vite 到 5.5.0` |

### 2.4 Scope（范围）

Scope 写你改的**功能模块**或**文件**：

```
feat(gaokao): ...      # 改了高考模块
fix(auth): ...         # 改了认证模块
refactor(storage): ...  # 改了存储模块
docs(api): ...         # 改了 API 文档
```

对应你的目录结构：
- `gaokao` / `kaoyan` / `employment` — 三大业务模块
- `auth` / `storage` / `security` — 基础设施
- `ui` / `mobile` — UI 相关
- `api` / `backend` — 后端相关

### 2.5 Subject（主题）

- 一句话说完，不超过 50 字
- 用**第一人称现在时**：「新增」而不是「新增了」或「已新增」
- 首字母大写（中文就写成「新增院校列表」，英文首字母大写）
- 结尾不加句号

## 三、Pull Request 规范（代码审查）

### 3.1 提 PR 的时机

✅ 应该提 PR：
- 写了 1-2 个小时的新功能，能独立测试了
- 修复了一个 bug，写了测试
- 改了几个文件但逻辑清晰

❌ 不要提 PR：
- 写了 10+ 个文件的改动（拆成 3-4 个小 PR）
- 代码没有自测过
- commit 说明是「update」「fix」这种模糊说法

### 3.2 PR 标题和描述格式

**标题** = commit message 的格式

```
feat(gaokao): 新增院校列表页面
```

**描述**：用 Markdown 写清楚三块

```markdown
## 改了什么
- 新增 js/gaokao.js 院校筛选逻辑
- 实现院校列表页面，支持按省份、层次、类型筛选
- 添加 css/gaokao.css 样式文件（移动端优先）

## 怎么测试
1. 用浏览器打开 index.html
2. 点击「院校库」按钮
3. 在筛选框选择「浙江省」，应看到浙江的院校
4. 点开某个学校卡片，应看到学校详情

## 截图或演示
[如果有就放这里，没有可以不写]

## 需要特别注意
- 数据目前是本地 mock 的，等后续提供真实数据后需要改接口
- 移动端在 360px 宽度测试过
- CSS 用了 Grid

## 关联的任务
- closes #12 (如果有关联的 GitHub issue，写这里)
```

### 3.3 Review 的人要检查什么

**被 @ 了要做的事**：

1. **第一眼**：PR 改了多少个文件？如果超过 15 个，可以问提交者拆成几个小 PR
2. **安全性**：
   - ❌ 有没有把用户输入直接拼进 `innerHTML`？（XSS 漏洞）
   - ❌ 有没有暴露 API 密钥、密码？
   - ❌ 有没有删除了原本有的权限检查？
3. **代码质量**：
   - ✅ 有没有 `console.log` 忘记删？
   - ✅ 变量名清不清楚？
   - ✅ 有没有重复代码可以提取？
   - ✅ 逻辑有没有明显问题？
4. **规范**：
   - ✅ 有没有超过 500 行的文件？
   - ✅ 样式有没有写死颜色值（应该用 CSS 变量）？
   - ✅ 有没有往 `legacy/` 里加代码？

**具体操作**：
- 打开 PR → **Files changed** 标签
- 对着代码逐行看，有问题点 `+` 加评论
- 如果只有很小的改动（打字错误、变量名建议），点 **Comment** 即可
- 如果有重大问题（逻辑错误、安全漏洞），点 **Request changes** 并说明理由
- 都没问题 → 点 **Approve** → 提交者自己 Merge

### 3.4 被拒了怎么办

如果 Review 者点了 **Request changes**：

1. **不要反驳，要改**（Review 者大概率是对的）
2. 在自己的分支上继续改
3. 改完后 commit 并 push（不要 amend，保留改动历史）
4. PR 会自动更新，Re-request review
5. 再过一遍

## 四、冲突处理（一定会遇到）

### 4.1 冲突怎么发生的

两个人改了**同一个文件的同一行**，Git 不知道该听谁的。

**关键点**：冲突不会丢失代码，只是让你选择。

### 4.2 冲突的样子

```javascript
<<<<<<< HEAD
const title = "院校库";        // 这是别人的改动（或当前分支）
=======
const title = "院校列表";      // 这是你的改动
>>>>>>> feat/school-list
```

### 4.3 三步解决冲突

**第 1 步**：打开冲突文件

VS Code 会自动高亮冲突区域，显示四个按钮：
- **Accept Current Change** — 保留上面的（别人的）
- **Accept Incoming Change** — 保留下面的（你的）
- **Accept Both Changes** — 两个都要
- **Compare Changes** — 并行显示两个版本

**第 2 步**：和队友商量选择

```javascript
// 商量后决定用"院校库"，删掉 <<< === >>>
const title = "院校库";
```

**第 3 步**：标记完成并提交

```bash
git add js/gaokao.js
git commit -m "merge: 解决与 main 的冲突"
git push
```

### 4.4 怎么减少冲突（最重要！）

| 做法 | 效果 | 投入 |
|------|------|------|
| 每天开工先 `git pull` | 减少 50% 冲突 | 5 秒 |
| 一个分支只干一件事，做完立刻 PR | 减少 30% 冲突 | 无额外投入 |
| 拆分代码（各组改不同文件） | 减少 60% 冲突 | 本来就要做 |
| 不同人改不同模块 | 减少 80% 冲突 | 规范管理 |

**最重要的**：每周一早上第一件事，全组一起 `git pull` 一遍。

## 五、日常工作流（每天重复）

### 5.1 早上开工

```bash
# 1. 进入项目目录
cd ~/Desktop/引路网站_v3

# 2. 切到 main（主分支）
git switch main

# 3. 拉取别人的改动（最重要！）
git pull

# 4. 看看有没有新分支
git branch -a

# 5. 新建自己的分支（以你的任务命名）
git switch -c feat/school-list

# 或者用长格式
git checkout -b feat/alice-school-list
```

### 5.2 写代码

```bash
# 用 VS Code 或任何编辑器打开文件
# 只改你认领的文件（见 02_9人分工与文件认领表.md）

# 改完后在浏览器打开 index.html 看效果
# ... 改代码 ... 测试 ... 改代码 ...
```

### 5.3 提交（每完成一个小功能就提）

```bash
# 1. 看看改了什么
git status

# 2. 看看具体改了哪些行
git diff

# 3. 把改动暂存
git add .
# 或者只暂存某些文件
git add js/gaokao.js css/gaokao.css

# 4. 提交并写清楚说明
git commit -m "feat(gaokao): 新增院校列表筛选"

# 5. 推到远程（第一次要加 -u）
git push -u origin feat/school-list

# 之后就直接
git push
```

### 5.4 提 PR（代码完成后）

1. 打开 GitHub 仓库首页
2. 会看到黄色横条：`Compare & pull request` → 点它
3. **Base 选 main**，Compare 选你的分支（feat/school-list）
4. 填写 PR 标题和描述（参考第三部分）
5. 右侧选 Reviewer（选 G0）
6. 点 **Create Pull Request**
7. 等 G0 审核通过后，你自己点 **Merge pull request**
7. 删除自己的分支（GitHub 会提示）

### 5.5 晚上收工

```bash
# 1. 看看有没有未提交的改动（不该有）
git status

# 2. 如果有，要么提交，要么暂存
git stash

# 3. 切回 main
git switch main

# 4. 拉一遍最新的
git pull
```

## 六、常见错误与救急

### 6.1 错误集合

| 错误信息 | 原因 | 怎么修 |
|---------|------|--------|
| `fatal: not a git repository` | 当前目录不是仓库 | `cd` 到项目目录，或先 `git clone` |
| `Permission denied (publickey)` | 用了 SSH 地址但没配密钥 | 用 HTTPS 地址，或配 SSH key（问 G0） |
| `failed to push some refs` | 远程比本地新 | `git pull --rebase` 后再 `git push` |
| `Your branch is ahead of 'origin/main'` | 本地有提交没 push | `git push` |
| `Your local changes would be overwritten` | 本地有改动没提交 | `git stash` 暂存，pull 完 `git stash pop` 恢复 |

### 6.2 救急命令

```bash
# ❌ 改错了文件（还没 add），想放弃改动（危险！会丢失改动）
git checkout -- 文件名

# ✅ 改错了文件（还没 add），想暂时存放
git stash

# ✅ 改错了文件（已经 add 但没 commit），想撤回
git reset HEAD 文件名

# ✅ 提交错了（commit 了但没 push），想撤回（保留改动）
git reset --soft HEAD~1

# ✅ 提交错了（commit 了但没 push），想完全撤销（丢失改动）
git reset --hard HEAD~1

# ✅ 提交错了（已经 push 了），不能用 reset，要用 revert
git revert HEAD

# ✅ 看看最近 10 次提交
git log --oneline -10

# ✅ 看某个文件每一行是谁什么时候改的
git blame 文件名

# ✅ 看某个分支有什么改动
git log main..feat/school-list --oneline
```

### 6.3 真的搞砸了？

**记住这三句话**：
1. **不要 `git push -f`**（会覆盖别人的代码，大罪）
2. **不要 `git reset --hard`**（除非你 100% 知道在做什么）
3. **不确定就问 G0**（问一下比折腾半小时强）

## 八、分支命名规范详解

### 8.1 命名格式

```
g<group>-<description>
```

### 8.2 完整例子

```
feat/school-list              # G1 新增院校列表
feat/mobile-header            # G1 改手机版导航栏
feat/login-bug                # G2 修复登录 bug
feat/whitepaper               # G3 写安全白皮书
feat/data-update              # G4 更新数据
feat/dark-theme               # G5 调整深色主题
feat/ci-config                # G0 配置 CI
```

### 8.3 规则

- ✅ 用英文、数字、连字符（`-`）
- ✅ 组号必须有（`g0`、`g1`、`g2` 等）
- ✅ 描述要有意义（`school-list` 好于 `list`）
- ❌ 不要用空格、下划线、中文
- ❌ 不要用 `dev`、`master`、`test` 这种通用名字

## 十一、名词解释（新人常问）

| 词 | 意思 | 类比 |
|---|---|---|
| **仓库（Repository）** | 整个项目的所有代码和历史 | 档案柜 |
| **提交（Commit）** | 保存一次改动的快照 | 游戏存档 |
| **分支（Branch）** | 独立的工作线 | 副本、平行世界 |
| **推送（Push）** | 上传到远程 | 上传到网盘 |
| **拉取（Pull）** | 下载远程的改动 | 从网盘下载 |
| **合并（Merge）** | 两个分支的改动合到一起 | 两份稿子合并 |
| **冲突（Conflict）** | 两个改动改了同一行 | 两人同时改了同一句话 |
| **暂存区（Stage）** | 提交前的中间站 | 购物车 |
| **工作区（Working Directory）** | 你电脑上看到的文件 | 手中的文件 |
