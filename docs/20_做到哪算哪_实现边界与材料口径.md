# 20 · 做到哪算哪：实现边界与材料口径

> **先给结论**：你这个想法是对的，而且**规则站在你这边**。
> 但有一条红线 —— **没做的不能写成做了**。踩了不是"扣分"的问题，是性质问题。
> 本文给你三档清单 + 可以直接抄的表述话术 + 答辩应答预案。

---

## 零、为什么"做到哪算哪"是合规的

### 赛事规则本身允许

挑战杯科技发明制作类分为两类：

| 类别 | 定位 | 评审看什么 |
|---|---|---|
| **A 类** | 科技含量较高、制作投入较大的作品 | 技术复杂度、创新性、完整度 |
| **B 类** | **投入较少、周期较短、为生产技术或社会生活带来便利的小制作** | **实用性、构思精巧、解决实际问题** |

**我们报的就是 B 类。** B 类的定位本来就是"小而美 + 有想法"，**不要求大而全**。

换句话说：一个**能完整跑通的小系统** + 清晰的技术演进路线，**比一个到处是半成品的大系统体面得多**。

### 而且"实事求是"本身就是加分项

评委见过太多吹上天的作品。**能清楚说出"哪些做了、哪些在设计中、为什么先不做"的团队，反而显得成熟。**

这句话可以直接写进申报书：

> 作品"已完成核心功能 X 项，另有 Y 项处于技术方案设计阶段，将在后续研究中逐步实现"。

这叫**诚实的野心**，不叫缺陷。

### ⛔ 但有一条红线

**不能把规划中的东西，写成已经实现的东西。**

举例说明什么是踩线：

| ❌ 踩线写法 | 为什么危险 |
|---|---|
| "本作品采用 Ed25519 数字签名实现匿名凭证" | 现场让你演示签名/验签，立刻露馅 |
| "系统已完成与院校数据库的对接" | 评委问"数据哪来的"，答不上来 |
| "实现了录取概率预测模型" | 会追问准确率和样本量 |
| "具备完整的用户风控体系" | 会问拦截了多少次攻击 |

**一旦被抓到一处夸大，你材料里所有的其他陈述都会被打上问号。** 这是最亏本的赌注。

### B 档 · 方案已成型 / 图纸阶段 📐

**这些可以写进"技术方案"章节，说"已完成设计"，但不能说"已实现"。**

| 功能 | 当前真实状态 | 国庆 6 天能产出什么 |
|---|---|---|
| **数据库表结构设计** | 无任何设计文档 | P9 出《数据库设计说明书》+ ER 图 |
| **院校录取真实数据源** | 内置示例数据（216 行），非真实 | P8 定数据源方案 + 采集一批样例数据 |
| **匿名凭证方案（G3 核心）** | **只有 SHA-256 密码哈希，55 行**<br>没有任何签名/凭证机制 | P6 出设计方案 + 流程图<br>明确用 tweetnacl.js |
| **风控 / 反虚假评价** | 完全不存在 | P7 出规则清单（3–5 小时版） |
| **服务端架构** | 无 `server/` 无 `api/`，一行没有 | 表结构 + 接口清单，纸上设计 |

#### ⚠️ 关于安全模块的准确说法（重要）

`js/05-core-security.js` 这个文件名叫"security"，但**它实际只有 55 行**，内容是：

```
✅ secureRandomToken()      —— 用 crypto.getRandomValues 生成随机码
✅ safeExternalHref()       —— 过滤危险协议的外链
✅ createPasswordRecord()   —— SHA-256 + 24 位随机盐 存密码
✅ 角色判断（学生/家长）
```

**它没有**：数字签名、Ed25519、证书、匿名凭证、防篡改链 —— 一样都没有。

所以答辩的时候：

- ✅ **可以说**："我们实现了基于 Web Crypto API 的密码加盐哈希存储，和外链协议白名单过滤。"
- ❌ **不可以说**："我们实现了匿名凭证系统 / 数字签名 / 防篡改。"

**这一条的建议话术**（让 P6 说）：

> "这是我们安全体系的**第一层**。应用层安全防护已经落地；身份层（匿名凭证）的技术方案我们已经完成选型和设计，计划在下一阶段实现。"

这句话既诚实，又把 G3 的价值说清楚了。

**这些放材料最后一章，作为演进路线。这部分的篇幅就是你说的"论文可以根据预测来"。**

| 方向 | 怎么在材料里写 |

| Ed25519 在校生匿名凭证签发 | "第三阶段：引入非对称签名，实现身份可验证且不泄露隐私" |

## 二、材料里的表述话术（可以直接抄）

### 对照表：同一件事，两种说法

| 你想表达的事 | ❌ 越界写法 | ✅ 恰当写法 |
|---|---|---|
| 匿名凭证还没做 | "实现了匿名身份认证" | "**完成匿名凭证技术选型与方案设计**，采用 Ed25519 椭圆曲线签名" |
| 没有真实数据 | "接入了院校录取数据库" | "**构建了规范化的数据模型**，支持真实数据源的批量导入" |
| 没有后端 | "具备服务端支撑" | "采用**前后端分离架构**，服务端接口契约已完成定义" |
| 录取概率是估算 | "实现了精准的录取预测" | "实现了基于位次换算的**录取概率估算模块**" |
| 只在本地跑 | "系统已上线运行" | "系统已在**本地与浏览器环境完整运行**，支持离线使用" |
| 安全做了基础部分 | "具备完整的安全防护体系" | "已实现**应用层基础安全防护**（加盐哈希 / 协议白名单）" |

### 万能句式的三个层次

给团队统一口径，按这三个词区分：

```
「已实现」     —— 代码就在那儿，随时能演示    ← 只有 A 档能用
「已完成设计」 —— 方案定了、文档写了、图纸画了  ← B 档
「规划中」     —— 想清楚了要做什么，还没动工    ← C 档
```

**任何人写自己的任务交付材料时，先问自己：这个功能，我今天能当场打开给评委看吗？**

- 能 → 用"已实现"
- 不能，但有完整设计文档 → 用"已完成设计"
- 只有个想法 → 用"规划中"

### 申报书/说明书标准开场模板

> 本作品为面向高考志愿决策场景的信息服务平台，定位于**科技发明制作类 B 类**。
>
> 作品已完成**前端主体功能 X 项**的实机开发，涵盖信息浏览、多维度筛选、横向对比、
> 经验分享、问答社区与家庭协同等核心业务闭环，并具备**完整的移动端响应式适配**。
>
> 安全体系方面，已完成应用层基础防护（加盐哈希存储、外链协议白名单）的落地；
> 密码学匿名凭证、服务端可信存储等模块**已完成技术方案设计与选型**。
>
> 后续将围绕真实数据接入、服务端落地、匿名凭证实现三个阶段持续迭代，
> 形成**演进路线清晰、工程规范可验证**的完整成果。

## 三、答辩应答预案（被追问时怎么接）

评委最常问的四个问题，准备好了就不慌：

### 问 1：「这个是你们做的吗？」

**别慌，这是常规问题，不是指控。**

> "是我们做的。前端这几个页面您可以随便点，我也可以当场改一个功能给您看。
> 我们合作的机制是 Git 版本管理，每一次改动都有提交记录和时间戳，
> 这是我们的仓库地址。"

**底气来源**：只要你的 GitHub 仓库推送上去了，**提交记录就是最硬的证据**。所以务必把 v3 推上去 —— 这不只是为了协作，**这是你的作品归属证明**。

### 问 2：「这个功能介绍得很详细，能演示一下吗？」（恰好是没做的）

> "这个功能目前处在方案设计阶段，还没有实机演示。
> 这是我们的设计文档和流程图。
> 我们之所以把它放在第二阶段，是因为它需要依赖服务端的搭建 —— 
> 我们优先保证了前端业务闭环的完整性和可运行性。"

**关键**：**主动给出替代物**（设计文档 / 流程图 / 数据库 ER 图）。评委问"能不能演示"时，最差的回答是"这个还没做完没东西看"，最好的回答是"代码还没写，但请您看我们的设计"。

### 问 3：「你们的数据哪来的？」

> "目前系统里是结构化示例数据。我们使用真实的数据字段结构
> （院校、批次、专业、最低分、最低位次、计划数），
> 真实数据的批量导入方案已经设计完成，计划在下一阶段接入官方公开数据。"

⚠️ **绝对不要现场编数据来源**。一旦说"来自阳光高考平台"之类具体来源，评委可能追问格式细节。

### 问 4：「和市面上的 XX App 比，你们的优势在哪？」

这是我们最强的一题，答案就是 **G3 可信** + **家庭协同**：

> "市面上多数产品做的是**信息聚合**，我们做的是**可信 + 共治**。
> 第一，经验分享者的在校生身份我们设计了可验证机制，解决虚假经验问题；
> 第二，我们设计了家庭协同模块，家长和孩子在同一个决策空间里沟通，
> 而不是各看各的。这两点是多数产品没有覆盖的。"

> ⚠️ 这里说"设计了"，不是"实现了"。一字之差，安全。

## 四、给全队的统一口径（开会时念这一段）

> 关于材料怎么写，我说一件事，大家记住：
>
> **我们要诚实，但不用自我贬低。**
>
> 诚实的意思是 —— 没写出来的代码，不能在纸上说写了。这是底线，
> 一旦被抓到，我们九个人的所有工作都会被怀疑，太不划算。
>
> 不自我贬低的意思是 —— **方案设计、技术选型、流程图、数据库 ER 图，
> 这些都是实打实的工作成果**，可以大大方方写进材料。学术界管这叫"已完成设计"。
>
> 所以每个人写自己的部分时，请用这三个词自我检查：
>
> - 能当场打开演示的 → 写「**已实现**」
> - 有完整设计文档的 → 写「**已完成设计**」
> - 只有想法的 → 写「**规划中**」
>
> 三个词用对了，我们的材料既诚实又漂亮。

## 五、国庆 6 天，三档分别怎么推进

| 档位 | 这 6 天做什么 | 谁在做 |
|---|---|---|
| **A 档** | **保住不退化** —— 任何人改完必须在本地跑通确认没坏；<br>Day 6 生成最终演示版 | 全体 + P1 把关 |
| **B 档** | **全部转成文档** —— 技术方案、ER 图、风控规则清单、<br>凭证设计说明 | P4 / P6 / P7 / P8 / P9 |
| **C 档** | **写进材料最后一章** —— 三阶段演进路线 | P1 统稿 |

**6 天产出比例建议**：

```
A 档（真代码）   ████░░░░░░  30%   —— 只补短板、修 bug、改文案
B 档（设计文档） ████████░░  50%   —— 这是主力战场
C 档（材料写作） ██████░░░░  20%   —— 申报书 + 说明书 + 佐证 PDF
```

> 这就是为什么我在 `docs/16` 里说：**国庆明确放弃后端编码**。
> 因为后端的产出目标是"设计说明书"，不是能跑的服务。这正好符合 B 档定位。

## 六、自查清单（材料提交前逐条过）

```
□ 材料里每个写「已实现」的功能，我都能当场打开演示
□ 每个写「已完成设计」的，都有对应的设计文档在 docs/ 里
□ 每个写「规划中」的，都放在"后续研究"章节，没混进成果章节
□ 没有任何一处暗示我们拥有真实院校数据
□ 没有任何一处暗示我们有服务器端 / 在线部署能力
□ 安全部分的表述限定在「SHA-256 加盐哈希」和「外链过滤」这两个真的东西上
□ 软著写成「申请中」，附提交截图，没有写成「已取得」
□ 团队成员名单和署名顺序，与 GitHub 提交记录能对应上
□ GitHub 仓库已经推送（可公开访问，作为归属证明）
□ 全文通读一遍，没有"最""首创""唯一"这类无法证明的绝对化用词
```

> 最后一条特别提醒：**"首创""唯一""国内领先"这类词，评委的第一反应是反感。**
> 换成"相较于多数同类产品，我们强化了……"效果更好也更安全。
