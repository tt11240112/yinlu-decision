> 版本：v1.0（院赛定稿）　日期：2026-09-27
> 状态口径：本文档对应方案 **B 级已交付**；「内容哈希存证」前端 API **已实现**；Ed25519 完整签名验签列入**复赛实施计划**。

## 一、要解决的问题（评委视角）

评委一定会问的两个问题：

1. **"你们怎么保证分享经验的人真是本校在校生？"** —— 任何人都能在网上自称"某大学大二学生"，经验贴的真伪无从判断。
2. **"内容会不会被篡改？我怎么知道看到的还是作者当初写的？"**

我们的回答：引路采用**后台实名、前台匿名**的匿名凭证体系 —— 平台在后台核验学籍后，用数字签名给学生签发一张"不含任何个人身份信息的凭证"，凭证随帖展示、任何人可独立验证。

## 二、设计原则

| 原则 | 含义 | 对应实现 |
|---|---|---|
| 最小披露 | 平台只知道"你是不是在校生"，不知道"发这条帖的是谁" | 凭证只含「在校生」标记 + 学校/专业/年级标签，不含姓名学号 |
| 可公开验证 | 不需要信任平台也能验证真伪 | 签名可用平台公钥在**任何人本地**校验 |
| 零依赖 | 双击 index.html 就能用，不引第三方库 | 哈希存证用浏览器原生 `crypto.subtle`；签名复赛引 tweetnacl.js（10KB，已获批准流程） |
| 防篡改 | 内容改动即被发现 | 凭证签名/存证覆盖**内容摘要**，而非仅覆盖身份 |

## 三、威胁模型

我们假设的攻击者与对应的防御：

| 攻击者 | 攻击手段 | 防御 |
|---|---|---|
| 冒充者 | 伪造"已验证在校生"徽章 | 徽章由平台私钥签发，伪造者没有私钥，验签必然失败 |
| 篡改者 | 修改已发布经验的内容（如改成绩、改结论） | 内容哈希与存证比对不一致，验签失败 |
| 重放者 | 把 A 的凭证复制给自己的帖子 | 凭证绑定作者 ID 与内容摘要，换内容即验签失败 |
| 好奇的平台内部人员 | 想知道"这条匿名帖子是谁发的" | 前台凭证不含身份信息；实名材料仅存后台核验记录，与发帖行为无直接关联字段 |

**明确不防**（诚实声明）：不防"用别人电脑登录发帖"、不防后台管理员主动作恶关联（这是中心化签发的固有边界，复赛可讨论门限签发/盲签名）。

## 四、总体方案：Ed25519 匿名凭证

### 4.1 凭证数据结构（设计）

```json
{
  "version": 1,
  "type": "yinlu-student-credential",
  "claims": {
    "enrolled": true,
    "school": "福建师范大学",
    "major": "软件工程",
    "grade": "2024级"
  },
  "subject": "u_8f3k…（用户 ID 假名，非真实身份）",
  "issuedAt": "2026-10-01T00:00:00Z",
  "expiresAt": "2027-07-01T00:00:00Z",
  "signature": "（Ed25519 签名，覆盖以上全部字段）"
}
```

关键点：`claims` 里**没有**姓名、学号、身份证号；`subject` 是平台内随机假名 ID；签名由平台持有的 Ed25519 私钥生成，公钥公开硬编码在前端，任何人可验。

### 4.2 凭证生命周期（六个环节）

1. **申请**：学生在"信任中心"发起认证，学籍材料只在后台受理（页面不上传、不公开）。
2. **核验**：管理员在后台将材料与学籍信息比对，人工审核。
3. **签发**：通过后，平台用 Ed25519 私钥对凭证（只含"在校生"标记）签名，发给学生。
4. **使用**：学生发帖时附带凭证；前端把帖子内容做摘要，与凭证一并绑定。
5. **展示**：其他用户看到「已验证在校生」徽章，作者其余信息保持匿名。
6. **验证**：任何人点击徽章，浏览器用平台公钥本地验签 + 比对内容哈希，立即得出真伪。

### 4.3 为什么选 Ed25519

- **签名短、验签快**：64 字节签名，验证毫秒级，适合纯前端浏览器验签。
- **实现成熟**：tweetnacl.js 约 10KB、纯 JS、无依赖、被广泛审计使用，符合"零依赖双击能开"的项目约束（引库需 P1 批准，已列入报备事项）。
- **不自己造轮子**：密码学铁律——算法实现一个比特写错就是全盘皆输，且写错的人自己看不出来。因此**绝不手写椭圆曲线运算**。

## 五、分级实施与现状

### 5.1 B 级（本次院赛，已完成 ✅）

**内容哈希存证** —— 证明"内容没被改过"，已在前端落地：

- 新增函数（位于 `js/05-core-security.js` 末尾，纯追加，不动已有代码）：
  - `computeContentHash(content)`：用浏览器原生 `crypto.subtle.digest("SHA-256", …)` 计算内容摘要；
  - `createContentAttestation(content, authorId)`：发帖时生成存证记录（哈希 + 假名作者 + 时间 + 算法标识）；
  - `verifyContentAttestation(content, attestation)`：展示时重新哈希比对，不一致即判定被篡改。
- 技术红线自查：✅ 未手写任何椭圆曲线/Ed25519 实现；✅ 未引入任何第三方库（原生 Web Crypto）。

边界说明：哈希存证能证明**内容完整性**（防篡改），不能证明**签发者身份**（防冒充）——后者由复赛的 Ed25519 签名补齐。这个取舍在 6 天冲刺内是安全工程上的正确顺序：先保证"改了能发现"，再追求"没签就能识破"。
