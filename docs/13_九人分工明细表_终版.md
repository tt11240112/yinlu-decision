## 第 0 章 · 为什么要这样分（明天开会先讲这段）

### 一句话结论

> **2 个网安全部进 G3 安全可信组；7 个计科里，你当组长，其余 6 人两两一组，
> 分守前端、业务、数据后端。**

### 为什么网安必须去 G3，而不是打散

| 理由 | 说明 |
|---|---|
| **这是唯一抄不走的差异化** | 全省做"高考志愿咨询网站"的队伍有一堆，做**可信经验分享**的几乎没有。评委一天看几十份，只有你们的作品里有"匿名凭证""防伪""透明度报告"，他才会停下来问 |
| **专业对口才有说服力** | 答辩时评委问"你们怎么防伪造 experience？"，网安专业的人答 Ed25519 签名 + 时间戳，和计科的人照本宣科念，可信度完全不同 |
| **打散等于自废武功** | 2 个人分散到各组，每人每周只能抽 2 小时搞安全，最后只能写个"我们有 XSS 过滤"——这个人人都会写，等于没有 |
| **材料上能写一行硬话** | 申报书里"本作品的安全模块由网络空间安全专业成员独立设计与实现"，这句话是加分项 |

> ⚠️ **绝对不要把 G3 砍成 1 个人。** 这是整个分工里最不能让步的一条。

### 为什么 G0 只放你 1 个人

你之前的问题不是"你在写代码"，而是**你在做人肉合并机**——
9 个人的改动全堆到你手上，你既要看懂、又要解决冲突、还要保证不崩。
最后变成你在写、其他人在旁观。

新方案要消灭的是**这个环节**，不是消灭你的技术产出。

| | 过去的你 | 现在的你 |
|---|---|---|
| 合并方式 | 9 人发代码，你手动粘贴 | 队友提 PR，GitHub 自动检查，你点 Merge |
| 冲突 | 你肉眼找 | 有冲突 GitHub 标红，谁改的谁负责解 |
| 加班 | 一个人熬到 3 点 | 每人只对自己的那份负责 |
| 技术产出 | 全队的活都是你干的，但**看不出来** | 你认领一块有边界的攻坚，Git 上**看得见** |
| 管理 | 没空做 | 有固定时间做 |

> **一句话**：不让你干的活是「替别人收拾残局」，不是「写代码」。

### 🆕 队长的第二身份：技术攻坚（结对制）

你说得对——**一个人啥也不干光审核，既浪费人力也说不过去**。
所以 P1 设置**双身份**：

```
P1 主身份  = G0 管理  （约 50% 精力）
P1 第二身份 = G4-B 后端结对攻坚（约 40% 精力）
P1 机动身份 = 谁忙援助谁（约 10% 精力）
```

#### 怎么实现：结对（Pair）

CODEOWNERS **允许一行写两个 owner**——任一人审核都算数。

```gitattributes
/server/   @P9 @P1        ← 后端是你和 P9 共有的，谁都能审核
/api/      @P9 @P1
```

这样你和后端的同学**写同一批文件也不会撞车**，
提 PR 时互相 review，甚至可以直接结对写（一个写、一个看）。

#### 为什么偏偏是后端

1. **后端是全队最难的活**——你说得没错，2 个人真不够
2. **后端是关键路径**——它不出来，前端/业务/安全全卡着
3. **后端的产出最"值钱"**——简历上"独立实现 REST API + 数据库设计"比调 CSS 有用得多
4. **你做后端不会跟组员抢功**——没人认领这块，不存在冲突

> 💡 **如果你其实更想去别组**（比如安全），把第二身份设成 G3 也完全可以。
> 规则只有一个：**你必须有一个「归属于自己、且别人不抢」的技术岗位**。

### 🆕 有人很忙怎么办：巴士因子预案

现实情况：有人保研、有人实习、有人课多，**不可能 9 个人都全职**。
尤其是网安的那位同学比较忙，这个必须有预案，不能等他掉链子才发现。

#### 做法：每个任务指定「备份责任人」

| 角色 | 主责人 | 备份人 | 触发条件 |
|---|---|---|---|
| 匿名凭证 / 哈希存证 | P6（网安） | P1 | P6 连续 1 周没提交 |
| 风控 / 合规文档 | P7（网安，忙） | P1 + P3 | **立刻启动**，不等待 |
| REST API | P9 | P1（结对，本来就在做） | 随时 |
| 院校数据录入 | P8 | P5 | P8 卡住超过 3 天 |
| 移动端适配 | P2 | P3（同组互备） | —— |

#### 三条规则

1. **忙的人只做 P0**（最小可演示版本），其余任务**公开转交**，不留灰色地带
2. **转交要留证据**：在群里说一句 + 改 CODEOWNERS + 提一个 PR，三选一，最少做第一项
3. **署名按实际产出算**——转交出去的任务，贡献算接手的人。**这比"挂名但不干活"公平得多**

> ⚠️ **对网安同学的具体建议**（开会时可以直接这么跟他谈）：
>
> 别让他做"从零搞密码学"这种需要整块时间的事，
> 给他**能切片完成的任务**：比如只负责**设计凭证方案并写出设计文档**（3–5 小时就能搞定一次），
> 具体实现由你在 W2 接手落地。
> **他能贡献的是专业判断，不是工时。** 这个区分清楚了，两边都不痛苦。

## 第 3 章 · 保障机制：为什么这次不会重演"一个人合并"

### 三道锁

```
第 1 道  CODEOWNERS       谁的文件谁审核，系统强制指派 Reviewer
第 2 道  分支保护         v3 分支禁止直接 push，必须走 PR
第 3 道  PR 模板          7 条自检不打完勾提不了 PR
```

### 老做法 vs 新做法

| 环节 | ❌ 老做法（上次） | ✅ 新做法（这次） |
|---|---|---|
| 传代码 | 群里发压缩包给你 | 提 PR，GitHub 记录一切 |
| 合并 | 你手动粘贴 | GitHub 自动合并，冲突会标红 |
| 冲突 | 你肉眼找 | 谁冲突谁自己解 |
| 出 bug | 不知道是谁改的 | `git blame` 一秒定位 |
| 贡献证明 | 靠记忆和感情 | Git 提交记录，客观可查 |
| 你的工作量 | 每天 4 小时合并 | 每天 10 分钟点 Merge |

### 四条铁律（写进群公告）

1. ⛔ **不在 `v3` 分支上直接写代码** —— 先 `Create branch`
2. ⛔ **不改 CODEOWNERS 里不是你的文件** —— 要改先在群里说，让人家同意
3. ⛔ **不手写 `index.html`** —— 改 `template/index.html` 后跑 `node tools/build-index.js`
4. ⛔ **不用 `git add .`** —— 会误加别人的文件

### PR 谁来审

| 情况 | 谁审 |
|---|---|
| 只改了自己认领的文件 | 同组搭档互审即可（P2↔P3、P4↔P5、P6↔P7、P8↔P9） |
| 跨组文件 | P1 审 |
| 改了 `tools/` `template/` `index.html` | 必须 P1 审 |
| 不确定 | 发群里，P1 判断 |

> **队长不是瓶颈。** 90% 的 PR 由队友互审就够了，你只做例外处理。
